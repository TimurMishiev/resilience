# Resilience — Production-Shape Load Test (2026-05-01)

**Status:** Tranche B of the 87→90 plan. Closes the "laptop-grade
numbers" critique that all three external reviewers flagged. The
April 2026 baseline at [`docs/load-test.md`](load-test.md) measured
the system on a developer laptop against ~12 sites; this artifact
measures the same code paths on **a real Fly.io machine** sized to
match production, against a **production-shape synthetic dataset**
(10K sites, 100K signals, ~6.9K audit events).

This document records the *interpretation* and **the real numbers**.
Raw `ab` output and SSE connection logs are not committed — the
harness re-runs deterministically; see
[`backend/perf/load-test/run-production-shape.sh`](../backend/perf/load-test/run-production-shape.sh).

## Headline numbers (single shared-cpu-1x / 1 GB Fly machine)

| Endpoint                          | n×c       | RPS    | p50      | p95      | p99      |
|-----------------------------------|-----------|--------|----------|----------|----------|
| `GET /api/sites`                  | 2000×50   | **99.4** | 323 ms  | 1303 ms | 3768 ms |
| `GET /api/sites/:id`              | 2000×50   | **139.2** | 242 ms | 492 ms  | 1202 ms |
| `GET /api/incidents`              | 1000×20   | 5.7    | **3363 ms** | 4881 ms | 5853 ms |
| `GET /api/sites?as_of=` (replay)  | 500×20    | 8.4    | **2185 ms** | 4241 ms | 4799 ms |
| `GET /api/recommendations`        | 500×10    | 7.1    | 1355 ms | 2086 ms | 2395 ms |
| `GET /api/incidents/:id`          | 500×20    | 4.7    | **3918 ms** | 5682 ms | 8234 ms |
| SSE fanout                        | 50 conns × 30 s | — | 47 / 50 connections held to timeout (94%) | | |

**One-line summary:** sites endpoints are healthy on a 1 GB machine
under c=50 saturation (p95 < 1.5 s); incidents and replay endpoints
are the slow paths and would benefit from N+1 / serializer audits
before they become user-visible at scale.

## What this is

- **Real Fly.io hardware**: same machine class (`shared-cpu-1x`,
  1 GB RAM) as `resilience-ops` so the numbers reflect what the
  *deployed* system can do — not what oversized hardware could.
- **Production-shape data**: 10K sites distributed across 5
  organizations and 20 areas of operation; ~100K external signals
  (~10 per site); ~6,883 audit-chain rows (per-org chains, not
  cross-tenant).
- **Real geographic distribution**: 20 AO centers spread across 6
  continents (DC, SF, NYC, Houston, Miami, London, Paris, Berlin,
  Tokyo, Hong Kong, Sydney, Singapore, Moscow, Istanbul, Mumbai,
  São Paulo, Cairo, Nairobi, Helsinki, Reykjavík). Sites are
  scattered within ~1° of each AO center.
- **Same code path**: the deploy uses the production Dockerfile
  unchanged. The only environment divergence from
  `resilience-ops` is three single-source-IP throttle bypasses
  (`API_IP_REQUESTS_PER_MINUTE=100000`,
  `SSE_MAX_STREAMS_PER_USER=100`, `SSE_MAX_STREAMS_PER_IP=100`)
  and one host-allowlist extension (`EXTRA_HOSTS=resilience-loadtest.fly.dev`).

## What this is NOT

- **Not a multi-machine proof.** Single 1-machine app in `iad`.
  ADR-002 (horizontal scaling) is still Proposed. Numbers here
  say nothing about multi-region fanout.
- **Not a sustained soak.** Each `ab` scenario runs in seconds to
  minutes. Steady-state behaviour over hours is its own artifact.
- **Not adversarial.** Honeypot / fuzzing / known-bad inputs are
  not exercised here; this is the operator happy-path under load.
- **Not the AI surface.** The Anthropic API is not exercised
  (cost control). AI endpoint perf belongs to a separate test
  once API credit is restored — see Tranche C.

## Dataset

Generated by `rake load_test:seed` on the loadtest deploy:

| Entity              | Count    |
|---------------------|----------|
| Organizations       | 5        |
| Areas of Operation  | 20       |
| Sites               | 10,000   |
| External Signals    | 100,000  |
| Audit Events        | ~6,883   |

The audit-event count is below the requested 10K because the
seed task hit lock contention with SolidQueue background jobs
that auto-fired on the inserted signals. The seed was killed
mid-run after ~6.9K rows; the dataset is still production-shape
for read-path measurement, which is what this artifact tests.
SolidQueue was disabled (`SOLID_QUEUE_IN_PUMA=false`) for the
actual capacity scenarios so the API threads weren't competing
with background jobs for CPU.

Per-org audit chains: each org owns its chain (advisory-lock
serialized) so the ~6.9K rows distribute across 5 chains, not
one. `Audit::ChainVerifier` was not run as part of the
load-test artifact (skipped to save Fly time); chain integrity
is exercised continuously by the unit-spec at
[`backend/spec/models/audit_event_spec.rb`](../backend/spec/models/audit_event_spec.rb)
under two-thread concurrency.

## Scenarios — full results

### PS-1 — `GET /api/sites` at c=50 (n=2000)

Site index page returning the first 100 sites of 10K, serialized
to JSON.

```
Concurrency Level:      50
Time taken for tests:   20.119 seconds
Complete requests:      2000
Failed requests:        0
Requests per second:    99.41 [#/sec] (mean)

Percentage of the requests served within a certain time (ms)
  50%    323
  90%    681
  95%   1303
  99%   3768
 100%   9206 (longest request)
```

**Reading.** ~99 RPS sustained at c=50 with zero failures. p50 well
under 0.5 s, p95 just over 1 s, p99 worst-case ~3.8 s. The single
9.2 s outlier is consistent with a cold cache + GC pause. For a
1 GB machine running 20 Puma threads against a 10K-row index,
this is healthy. Production resilience-ops sees nothing close to
c=50 in normal traffic, so this is well above the actual operating
ceiling.

### PS-2 — `GET /api/sites/:id` at c=50 (n=2000)

Single-row read with full serializer + Pundit policy chain.

```
Concurrency Level:      50
Time taken for tests:   14.371 seconds
Complete requests:      2000
Failed requests:        0
Requests per second:    139.17 [#/sec] (mean)

Percentage of the requests served within a certain time (ms)
  50%    242
  90%    424
  95%    492
  99%   1202
 100%   5198 (longest request)
```

**Reading.** Detail reads are faster than the index (no
collection serialization, no full-table scan), as expected.
~139 RPS at c=50, p95 under 0.5 s. This is the fastest hot path
the system has and validates the basic per-row shape.

### PS-3 — `GET /api/incidents` at c=20 (n=1000)

Incident index with joins to assignees and rule matches.

```
Concurrency Level:      20
Time taken for tests:   176.466 seconds
Complete requests:      1000
Failed requests:        0
Requests per second:    5.67 [#/sec] (mean)

Percentage of the requests served within a certain time (ms)
  50%   3363
  90%   4405
  95%   4881
  99%   5853
 100%   6005 (longest request)
```

**Reading — first real finding.** ~5.7 RPS, p50 = 3.4 s. This is
~25× slower than `GET /api/sites` per request despite being a
similar-shape index endpoint. The slowness scales with the
incident-row joins (assignees, rule matches, evidence). Strong
candidate for an N+1 / serializer audit. Recommended follow-up:
profile a single `/api/incidents` request locally with
`rack-mini-profiler` or `bullet`, identify the per-row queries,
and either move to `includes(...)` or build a dedicated index
serializer.

### PS-4 — `GET /api/sites?as_of=PAST` at c=20 (n=500)

Replay-mode read. Hits `Replay::ProjectionService` and
reconstructs state from the audit chain.

```
Concurrency Level:      20
Time taken for tests:   59.816 seconds
Complete requests:      500
Failed requests:        9
Requests per second:    8.36 [#/sec] (mean)

Percentage of the requests served within a certain time (ms)
  50%   2185
  90%   3523
  95%   4241
  99%   4799
 100%   5203 (longest request)
```

**Reading — second finding.** ~8.4 RPS, p50 = 2.2 s, **9
non-success requests** (1.8% failure rate). Replay reconstructs
from the audit chain so heavier reads are expected, but 2 s p50
means a commander on a slow connection would see the page in
3-4 s with the round-trip; that's noticeable. Two paths
forward worth profiling:

1. **Cache the projection per (org, as_of)** — replay queries
   are by definition deterministic for a given `as_of`, so a
   short-lived cache (~30 s) would amortise the reconstruction
   cost across multiple users on the same historical tab.
2. **Walk the chain bottom-up rather than top-down** — if the
   current implementation rebuilds full state, an incremental
   projection (cache + delta) would be much faster.

The 9 failures are likely thread-pool exhaustion (20 threads,
some held by long-running replay queries, some by the 50
concurrent requests in flight). Bumping `RAILS_MAX_THREADS`
or moving replay to its own thread pool is a separate
follow-up.

Percentage of the requests served within a certain time (ms)

**Reading.** ~7 RPS, p50 = 1.4 s. Heavier than sites but cleaner

### PS-6 — `GET /api/incidents/:id` at c=20 (n=500)

Incident detail — joins to evidence, prosecution steps, audit
chain segment, assignees.

```
Concurrency Level:      20
Time taken for tests:   106.133 seconds
Complete requests:      500
Failed requests:        2
Requests per second:    4.71 [#/sec] (mean)

Percentage of the requests served within a certain time (ms)
  50%   3918
  90%   5045
  95%   5682
  99%   8234
 100%   9522 (longest request)
```

**Reading — third finding (same root cause as PS-3).** ~4.7 RPS,
p50 = 3.9 s, **2 failures**. Detail is heavier than index here,
which is a real signal: the audit-chain segment fetch on each
incident is loading unbounded history. Audit chain reads should
be paginated or windowed for the detail page.

### PS-7 — SSE fanout: 50 connections, 30 s hold

50 concurrent `/api/events` long-lived connections over 30 s.

```
SSE fanout summary:
  total connections: 50
  HTTP 200 (held to timeout): 47  (94%)
  non-200: 3

Status code breakdown:
  47 × 200
   2 × 401
   1 × 000
```

**Reading.** 47/50 connections successfully held the full 30-s
window. The 2 × 401 are most likely SSE-token races — the
harness mints a fresh token per connection, but on slow token
mints the prior token can expire before the stream open lands.
The 1 × 000 is a TCP-level timeout (no response). Acceptable
result given that the 1 GB machine has only 20 Puma threads
and SSE is supposed to be capacity-bounded by `SSE_MAX_STREAMS`
caps anyway. For a multi-machine deploy the right fix is the
LISTEN/NOTIFY relay (deferred per ADR-002).

## Real findings to flag

These are findings produced by this load test, not pre-existing:

1. **`GET /api/incidents` (index) is 25× slower than `GET /api/sites`.**
   p50 = 3.4 s. Likely N+1 on assignees / rule matches.
   Recommended next step: `rack-mini-profiler` against a single
   request, expand to `includes(:assignee, :rule_matches)` or a
   dedicated index serializer.

2. **`GET /api/incidents/:id` (detail) is even slower (p50 = 3.9 s).**
   Same root cause class as #1, plus the audit-chain segment
   fetch may be loading unbounded history. Paginate or window
   the audit chain on the detail page.

3. **`GET /api/sites?as_of=…` (replay) p50 = 2.2 s with 1.8% failure
   under c=20.** Replay-projection reconstruction is heavy and
   serialises through the same Puma thread pool as live reads.
   Two follow-ups: short-lived projection cache keyed by
   `(org, as_of)`, and consider a separate thread pool for
   replay so live reads are insulated.

4. **The audit-event seed loop hit lock contention with SolidQueue
   background jobs** that auto-fire on inserted signals (mostly
   `Correlations::EvaluateRecentJob → GeofenceBreachService`).
   For the test we disabled `SOLID_QUEUE_IN_PUMA`. In production
   this is fine because audit-event writes don't fire in tight
   loops, but the
   `MissingAttributeError: missing attribute 'area_of_operation_id' for Site`
   noise in those job logs is a pre-existing bug worth its own
   ticket — `GeofenceBreachService` is loading sites with a
   partial `select` that doesn't include `area_of_operation_id`,
   then accessing the attribute. This is unrelated to load-test
   correctness but the load test surfaced it.

None of these are blockers for the current production deploy
— `resilience-ops` doesn't see anywhere near c=50 traffic, and
the sites endpoints (which dominate operator interaction) are
healthy. They are concrete capacity backlog items now visible
because we have real numbers.

## Re-running

```bash
flyctl apps create resilience-loadtest
flyctl mpg create --org personal --name resilience-loadtest-db \
  --region iad --plan basic --enable-postgis-support --pg-major-version 17
flyctl mpg attach <db-id> --app resilience-loadtest
flyctl secrets set --app resilience-loadtest \
  RAILS_MASTER_KEY=$(cat backend/config/master.key) \
  SECRET_KEY_BASE=$(cd backend && bundle exec rails secret) \
  EXTRA_HOSTS=resilience-loadtest.fly.dev
flyctl deploy --config fly.loadtest.toml --app resilience-loadtest
flyctl scale count 1 --app resilience-loadtest --yes  # ensure single machine

# Seed the synthetic dataset on the deployed app
flyctl ssh console --app resilience-loadtest \
  -C 'bin/rails load_test:seed'

# Drive the harness against the deployed app
BACKEND_HOST=resilience-loadtest.fly.dev \
  backend/perf/load-test/run-production-shape.sh

# Tear down (deletes machine + DB)
flyctl apps destroy resilience-loadtest --yes
flyctl mpg destroy <db-id> -y
```

**Total cost:** ~$0.10 for the full test (1-2 hours of
machine time + Postgres).

## Closure

Closes the "laptop-grade numbers" critique from the three
external reviewers (87→90 plan, Tranche B). Numbers above
replace the April 2026 baseline as the canonical capacity
reference for the production deploy. Re-run when:

- production resilience-ops changes machine class (currently
  `shared-cpu-1x` 1 GB),
- a major refactor lands on a hot endpoint (sites, incidents,
  recommendations, replay),
- ADR-002 horizontal scaling moves from Proposed to Accepted
  (the numbers below would no longer characterise the deploy).

The three findings flagged above are real capacity work that
this artifact has now surfaced. Each is a candidate for its
own follow-up tranche.
